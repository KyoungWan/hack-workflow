# 데이터 검증

제공 데이터를 실제로 읽어 분석·구현에 사용할 수 있는 범위와 품질 문제를 확인한다. 사용자가 핵심 문제와 판단 근거를 이해할 수 있도록 단계별로 짧게 설명한다. README 해석의 질문형 목차는 이 기능에서 반복하지 않는다.

## 1. 맥락과 데이터 구조 파악

- README·데이터 설명·기존 검증 코드와 진행 기록을 읽는다. 목적, 사용할 대상·기간, 제출 조건 중 이미 명시된 것은 다시 묻지 않는다.
- 파일별 헤더·표본 행·기초 집계를 확인하고 아래 표를 간결하게 작성한다. 큰 파일 전문이나 모든 컬럼을 대화에 쏟지 않는다.

| 파일 | 무엇을 기록했는가 | 한 행의 의미 | 주요 키·단위·기간 | 다른 파일과의 관계 |
|---|---|---|---|---|

- 중요한 파일에서 실제 한 행을 골라 쉬운 문장으로 풀어 설명한다. 파일명과 행 번호 또는 식별 키를 남긴다. 사용자가 이미 이해한 파일은 반복하지 않는다.
- 빈칸을 ‘없음’, 0을 ‘정상’, 상태 코드를 임의의 업무 의미로 해석하지 않는다. 문서와 실제 값이 다르면 불일치로 기록한다.
- 필드의 자료형과 업무 의미를 구분한다. 결과에 영향을 주는 단위·분모·기준 시점, 누적값과 증분값, 이벤트 발생 시각과 처리 시각을 문서·실제 값에 연결해 확인한다. 이름만으로 의미를 확정하지 않는다.
- 구조·검증 순서를 짧게 설명한 뒤 실제 품질 점검을 진행한다. 처음부터 전체 과제의 분석·최적화까지 확대하지 않는다.

## 2. 파일 내부 품질 검사

실제 데이터 전체를 코드로 검사하되 관련 없는 검사는 생략한다.

- 필수 파일·열·값, 빈 파일, 열 수·인코딩·파싱 오류.
- 숫자·날짜·시각 형식과 범위, 단위, 상태 코드의 허용값.
- 식별자 앞자리 0과 빈 값·0·false가 읽기·변환 과정에서 구분되어 보존되는지 확인.
- 완전 동일 행과 업무 키 중복을 구분하고, 중복 키 사이의 값 충돌도 확인.
- 결측치의 비율·분포·발생 패턴, 상수 컬럼과 급격한 분포 변화.
- 날짜 범위·구간별 건수, 혼합 날짜 형식·시간대·자정 경계. 파싱 성공만으로 의미가 맞다고 판단하지 않음.
- 해당 과제에서 중요하면 완료·미완료·미판정과 기본값, 기록 시점·결과 확정 지연을 구분.

명시된 형식·참조 위반은 오류로, 근거가 부족한 이상치는 확인 필요로 분류한다. 특정 결측률·이상치 임계값을 모든 과제에 고정하지 않는다. 표본 점검만 수행했다면 전체 검증으로 보고하지 않는다.

## 3. 파일 간 관계와 병합 검증

- 참조 ID가 실제 존재하는지, 파일별 대상·기간·상태 정의가 일치하는지 검사한다.
- 병합이 필요하면 키의 유일성, 예상 관계(1:1·1:N 등), 목표 집계 단위를 먼저 확인한다. 모든 파일을 한 테이블로 합치지 않는다.
- 병합 전후 행 수, 고유 대상 수, 매칭률, 미매칭 대상과 의도하지 않은 행 증식을 확인한다.
- 핵심 합계·분모가 보존되는지 확인한다. 제외·가중·집계 단위가 달라지면 이유와 영향을 설명한다.
- 데이터로 확인되는 업무 규칙을 점검한다. 예: 대상자의 누락·중복, 날짜별 상태 모순, 시간 순서. 다른 과제의 도메인 규칙을 그대로 가져오지 않는다.

## 4. 이상 발견과 확인 질문

- 데이터·코드로 확인 가능한 것은 직접 검사한다. 업무 정의·단위 의미·제외 기준처럼 자료로 결정할 수 없는 것은 추측으로 확정하지 않는다.
- 중요한 의문은 관측한 값·대상·차이와 함께 사용자에게 담당자 질문 문안을 제공한다. 답에 따라 어떤 판단이 달라지는지도 한 줄로 설명한다.
- 필요한 상황에서는 ‘무엇을 뜻하나요?’라는 확인형 질문 또는 ‘이런 차이를 확인했는데 관련 운영 변화가 있었나요?’라는 중간 보고형 질문을 제안한다. 질문을 억지로 만들거나 이미 확인된 내용을 반복하지 않는다.
- 담당자에게 직접 메시지를 보내지 않는다. 사용자가 전달한 답변을 받아 확인된 사실로 반영한다. 사용자 추정과 담당자 확인을 구분한다.
- 답변이 필요한 처리·결론만 보류하고 나머지 검증은 계속한다. 답변 부재를 동의로 간주하지 않는다.

## 5. 처리와 재현성

- 원본을 삭제·대치·보정하거나 중복을 임의 제거하지 않는다. 이상한 값이라는 이유만으로 오류라고 단정하지 않는다.
- 정제나 변환이 필요한 경우 이유와 처리 기준을 설명하고, 사용자 지시와 과제 범위에 맞춰 파생본에 적용한다. 의미가 미확인된 변경은 보류한다.
- 처리 전후 행 수·대상 수·주요 집계와 제외된 대표 사례를 비교한다. 핵심 결과를 바꾸는 처리에는 대안 처리의 영향을 확인한다.
- 재실행 가능한 검증 코드와 결과 요약을 기존 프로젝트 구조에 맞춰 저장한다. 기존 검증기를 재사용할 수 있으면 중복 구현하지 않는다.
- 오류는 가능하면 파일·행·식별 키·필드·문제 값·이유로 추적되게 기록한다. 민감한 값은 그대로 노출하지 않는다.
- 주요 집계는 별도 집계 경로나 원본 표본으로 교차 확인한다. 같은 함수의 재실행을 독립 검증으로 부르지 않는다.
- 확인된 업무 규칙에서 수작업으로 기대값을 계산할 수 있는 작은 사례를 만들고 실제 처리 결과와 비교한다. 정상 사례와 결과에 영향을 주는 빈 값·경계·중복·모순 사례를 선택한다. 정렬 불변성이나 부분합과 전체합의 일치 등은 해당 업무에서 성립할 때만 검사한다.
- 파생 파일을 저장했다면 다시 읽어 핵심 집계·식별자·날짜·형식이 유지되는지 확인한다. JSON의 NaN이나 날짜 직렬화처럼 실제 출력 형식에 해당하는 문제를 점검한다. 검증만 요청받은 경우 이 검사를 위해 불필요한 파생 파일을 만들지 않는다.

## 6. 정상·오류 변경 예제

과제 또는 사용자가 변경 데이터 예제를 요구할 때 수행한다.

- 정상본은 형식만 바꾼 복사본 대신 의미 있는 내용 변경을 포함하고, 오류본은 어떤 규칙을 위반했는지 명확히 한다.
- 변경하지 않은 파일은 원본을 재사용할 수 있다. 파일마다 개별 예제를 만들지, 여러 변경을 묶을지는 요청 범위에 따른다.
- 파일 묶음·변경 위치·전후 값·예상 결과를 기록하고 실제 검증기로 정상본 통과와 오류본 거부를 확인한다. 예상 결과를 실제 검증 대신 하드코딩하지 않는다.
- 입력 검증 통과와 후속 계산 성공을 구분한다. 계산 코드가 이미 있고 변경 반영 확인까지 요청받았다면 변경 결과도 확인한다.

## 진행과 완료

- 주요 단계가 끝나면 ‘확인한 것 / 중요한 문제 / 미확인 사항 / 다음 할 일’을 짧게 알린다. 매 파일·검사마다 승인을 요청하지 않는다. 사용자가 단계별 진행을 원하면 해당 경계에서 기다린다.
- 최종 요약은 검증 범위, 통과·실패·확인 필요 항목, 영향, 재실행 명령, 남은 질문을 포함한다. 근거 없는 ‘데이터 이상 없음’ 결론을 쓰지 않는다.
- 대화 중 확인된 근거와 질문은 기존 기록 위치에 모은다. 전체 대화 기록이나 별도 보고서·진도 파일을 자동으로 만들지 않는다.
- 이 기능만으로 인증 웹, 데이터 관리 UI, 최적화 엔진이나 제출 보고서를 자동 구현하지 않는다. 다른 기능은 명시적인 요청으로 전환한다.
