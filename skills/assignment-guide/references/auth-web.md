# 인증 웹 구현

업무 기능을 연결하기 전, 로그인과 세션·역할별 접근 제한이 동작하는 웹 기본 틀을 구현한다. 매니저 역할이나 Admin 계정 관리 기능은 포함하지 않는다. 필요하면 사용자의 별도 요청으로 다룬다.

## 1. 대화로 결정하기

구현 전에 다음을 사용자에게 대화형으로 확인한다. 선택지를 제공하는 입력 도구가 있으면 사용하고, 없으면 짧은 번호 선택 질문으로 묻는다. 이미 명시적으로 답한 항목은 반복해서 묻지 않는다.

1. **기술 스택**: 기본은 Next.js + SQLite. 그대로 사용할지, 다른 스택을 사용할지 확인한다. 기존 프로젝트와 충돌하는 경우 현재 스택을 알리고 선택받는다.
2. **사용자 역할**: 유저·관리자·Admin 중 구현할 역할을 선택받는다. 여러 역할을 선택할 수 있다. 각 역할의 화면 접근 범위를 확인하며 관리자와 Admin을 같은 역할로 임의 통합하거나 불필요하게 모두 만들지 않는다.

Admin을 선택하면 Admin 페이지 접근을 제공한다. 다른 역할은 해당 역할용 빈 화면을 제공한다. 관리자와 Admin을 함께 선택했다면 차이가 불명확할 때만 권한 차이를 추가로 묻는다. 답변을 기다리는 동안 기존 코드·설정은 살펴볼 수 있지만 스택·역할에 의존하는 구현은 시작하지 않는다.

## 2. 구현 결과

- ID·비밀번호 로그인 화면과 잘못된 자격 증명 안내.
- 선택한 역할별 빈 화면과 로그인 후 적절한 화면으로의 이동.
- 로그인 상태와 로그아웃 버튼. 업무 데이터나 과제의 핵심 기능은 추가하지 않는다.
- 미로그인 및 권한 없는 사용자의 페이지·API 접근을 서버에서 차단.
- 계정·비밀번호 해시·세션의 DB 저장과 재실행 가능한 초기 계정 준비.
- 필요한 환경변수 예제와 짧은 실행·역할별 접속 안내. 실제 비밀값은 문서나 코드에 기록하지 않는다.

기존 인증이 있으면 재사용하고 별도 로그인 앱을 중복 구현하지 않는다. README의 명시적인 요구가 기본값과 충돌하면 충돌을 알리고 과제 요구에 맞춰 조정한다.

## 3. 서버 세션 구조

기본 스택에서는 SQLite에 다음 정보를 저장한다. 구체적인 테이블명은 기존 구조에 맞춘다.

- 사용자: 사용자 ID, 로그인 ID, 비밀번호 해시, 역할.
- 세션: 세션 토큰 해시, 사용자 ID 참조, 만료 시각.
- 브라우저 쿠키: 충분히 무작위인 불투명 세션 토큰. 사용자 ID·역할·만료 정보를 토큰 내용으로 인코딩하지 않는다.

요청마다 토큰 해시로 유효한 세션을 찾고 만료를 확인한 뒤 사용자 테이블의 현재 역할로 권한을 판단한다. 클라이언트가 보낸 사용자 ID·역할을 권한 근거로 쓰지 않는다. JWT는 기본 구현으로 사용하지 않는다.

- 쿠키는 HttpOnly·SameSite를 설정하고 HTTPS 환경에서는 Secure를 사용한다.
- 로그인 성공 시 세션을 새로 발급하고 로그아웃 시 서버 세션을 폐기한다.
- 비밀번호는 검증된 비밀번호 해시 함수로 저장한다. 원문 비밀번호와 원문 세션 토큰을 DB·로그에 저장하지 않는다.
- 로그인 시도 제한과 상태 변경 요청의 출처 검증을 적용한다.
- 초기 계정 정책은 선택한 역할과 과제에 맞춘다. 사번 기반 비밀번호, 회원가입, 강제 비밀번호 변경, 계정 관리 UI를 자동으로 추가하지 않는다.

## 4. 완료 기준

다음을 실제로 검사하고 통과·실패·미검증을 구분해 보고한다.

1. 선택한 각 역할의 계정으로 로그인하고 해당 역할 화면에 접근할 수 있다.
2. 새로고침 후에도 유효한 로그인 상태가 유지된다.
3. 미로그인 사용자는 보호 페이지·API에 접근할 수 없다.
4. 다른 역할의 페이지·API에 직접 접근해도 차단된다. Admin 페이지는 Admin 권한으로 검사한다.
5. 로그아웃하면 기존 세션이 폐기되고 보호 페이지·API에 다시 접근할 수 없다.
6. 서버 재시작 후 같은 DB의 계정이 유지되며 다시 로그인할 수 있다.

계정 유지와 세션 유지는 구분한다. 유효 세션을 DB에 보존한 경우 재시작 후에도 만료·폐기 여부에 따라 처리되는지 확인한다. 역할을 하나만 선택했다면 역할 간 비교가 적용되지 않는 이유를 명시하고 미로그인 접근 차단은 확인한다. 테스트는 임시 DB와 확인용 계정으로 수행해 기존 계정을 훼손하지 않는다.

실행할 수 없는 검사는 이유와 재실행 방법을 남긴다. 화면이 만들어졌다는 사실만으로 인증 구현 완료를 선언하지 않는다.


## 5. 동봉 모듈 활용

Next.js + SQLite로 새 인증을 만들 때는 다음 코드를 기본 뼈대로 활용한다. 기존 인증이 있다면 무조건 덮어쓰지 말고 호환되는 부분만 재사용한다. 다른 스택을 선택했다면 파일을 강제로 복사하지 않고 같은 동작을 해당 환경에 맞게 구현한다.

- [crypto.mjs](../assets/auth/crypto.mjs): salt+scrypt 비밀번호 해시·검증, 무작위 토큰 생성, 토큰 SHA-256 해시.
- [schema.sql](../assets/auth/schema.sql): 사용자·세션 테이블과 인덱스. SQLite DB 구조를 생성하는 SQL 파일이며 별도 네임스페이스를 뜻하지 않는다.
- [sessions.mjs](../assets/auth/sessions.mjs): SQLite 연결을 주입받는 issue / identity / revoke. Node 내장 SQLite와 better-sqlite3의 동기 연결에 대응한다.
- [common.test.mjs](../assets/auth/common.test.mjs): 파일 SQLite의 재시작·역할 변경·만료·폐기 검증.

### 적용 순서

1. 사용자가 확정한 스택·역할을 확인하고 모듈을 읽는다.
2. 프로젝트의 서버 코드 위치에 필요한 파일을 복사하고 import·역할 목록을 조정한다. 스킬 설치 경로를 앱 런타임에서 직접 참조하지 않는다.
3. 환경변수로 정한 DB 경로에 연결하고 schema.sql을 실행한다. foreign_keys는 연결마다 활성화한다. 기존 DB의 구조 변경은 CREATE IF NOT EXISTS만으로 처리되지 않으므로 필요한 마이그레이션을 별도로 다룬다.
4. sessionStore(db, { ttlMs })를 구성한다. TTL은 환경설정에서 읽어 유효성을 검사하고 쿠키 수명과 맞춘다. 원문 토큰은 HttpOnly 쿠키에만 전달한다.
5. 로그인·로그아웃 처리, 쿠키 설정, 서버 권한 가드, 초기 계정, CSRF와 로그인 제한을 연결한다. 모듈 복사만으로 웹 인증이 완료됐다고 간주하지 않는다.
6. 동봉 테스트와 실제 Next.js 페이지·API·재시작 검증을 실행한다. 기본 모듈 테스트는 Node.js 24 환경에서 `node --test assets/auth/common.test.mjs`로 실행할 수 있다(스킬 폴더 기준). 프로젝트에 옮겼다면 해당 경로를 사용한다.

### identity와 접근 허용의 구분

- 로그인만 필요한 기능: identity(token)이 null이면 거부한다.
- 역할 제한 기능: null 검사 후 user.role이 허용된 역할인지 추가 검사한다. identity가 null이 아니라는 이유만으로 Admin 기능을 허용하지 않는다.
- 본인 데이터 기능: 로그인한 user.id로 조회 범위를 제한하거나 대상 데이터 소유자와 일치하는지 확인한다. 요청에서 받은 사용자 ID만으로 허용하지 않는다.
- API는 미로그인 401 / 역할 불일치 403을 반환한다. 페이지는 로그인 또는 접근 거부 안내로 이동하되 보호 내용을 먼저 렌더링하지 않는다.

### 템플릿의 범위

- schema.sql의 user/admin은 기본 예시다. 선택한 역할에 맞춰 DB 제약과 가드를 함께 수정한다. 매니저는 추가하지 않는다.
- 동기 scrypt는 작은 기본 앱의 선택이다. 고부하 환경에서는 비동기 해싱 등 실행 특성에 맞게 조정한다.
- 로그인 제한은 실패 횟수를 기준으로 제한·성공 시 초기화하는 정책을 기본으로 하되 과제 요구가 있으면 따른다. 입력 길이와 환경변수도 검사한다.
- 공통 모듈은 5회 독립 구현의 공통 동작을 정규화한 것이다. 전체 앱·쿠키·CSRF까지 검증을 대신하는 완성 인증 라이브러리는 아니다.
