# 요구사항 대비 구현 점검

README의 요구사항을 현재 코드·화면·API·데이터·검증 근거와 대조한다. 누락과 검증 공백을 찾아 우선순위를 제시하는 기능이며, 요청 전에는 코드를 수정하지 않는다.

## 1. 점검 범위 정하기

- README와 연결된 과제 문서·제출 양식을 읽는다. 제공 원문은 수정하지 않는다.
- 현재 사용자 지시, 기존 결정 기록, 코드 상태를 확인한다. 이전 완료 보고만 믿지 않고 실제 구현과 연결을 확인한다.
- 사용자 변경 지시와 원문이 충돌하면 두 기준을 구분한다. 최신 지시를 따랐다는 이유로 원문 충족으로 처리하지 않는다.
- 명시된 요구를 기능·운영 규칙·입력/오류 처리·역할·저장/실행 환경·제출물 등 해당 과제에 맞게 묶는다. 일반적인 모범 사례를 과제 필수 요구로 추가하지 않는다.
- 독립적으로 판정할 수 있는 단위로 나눈다. 한 항목에 정상 동작과 실패 시 동작이 함께 있으면 필요한 만큼 분리한다.

## 2. 실제 연결과 근거 확인

- 웹 기능은 화면 진입점 → 호출 API/서버 처리 → DB·입력·결과까지 연결을 추적한다. 파일이 존재하는 것과 현재 사용 가능한 기능을 구분한다.
- 실행 코드가 따로 있어도 현재 화면이 예시·고정 산출물만 표시한다면 실제 재계산 연결을 확인한다. 도메인별 알고리즘을 임의로 바꾸지 않는다.
- 과제가 변경 입력·기간·역할 등을 요구하면 기본 예제 외 조건에서도 반영되는 구조와 검사 근거가 있는지 확인한다.
- 오류 처리, 기존 결과 보존, 미완료·미생성 상태는 요구에 해당할 때 확인한다. 로그인 버튼만으로 권한 통제가 구현됐다고 판단하지 않는다.
- 설정·초기화·영속 저장·컨테이너 등은 파일 존재와 실행 검증을 분리한다. 문서 명령과 실제 스크립트·경로가 일치하는지 확인한다.
- 테스트 파일을 읽고 어떤 요구를 실제로 검사하는지 확인한다. 과거 화면 기준 테스트, 실행하지 않은 테스트, 현재 코드와 무관한 성공 기록을 검증 근거로 쓰지 않는다.
- 다른 에이전트의 성공 보고만으로 통과 판정하지 않는다. 실제 검사 결과와 해당 입력·코드 상태·검사 범위를 확인한다.
- 검색 결과가 없다는 이유만으로 미구현을 확정하지 않는다. 관련 진입점·설정·호출 경로를 확인하고 확인할 수 없으면 미검증으로 남긴다.

## 3. 상태 판정

각 요구사항에 하나의 대표 상태를 부여하고 필요하면 설명에 세부 검증 상태를 적는다.

| 상태 | 기준 |
|---|---|
| 완료 | 요구 범위가 구현·연결되어 있고 해당 동작의 유효한 검증 근거가 있음 |
| 부분 구현 | 일부 조건·흐름·역할·예외가 누락되었거나 요구와 다른 동작을 확인함 |
| 미구현 | 관련 경로를 확인했으며 필요한 기능·산출물이 구현되지 않음 |
| 미검증 | 구현은 있어 보이지만 실행·접근·환경·자료 부족으로 충족 여부를 확인하지 못함 |

- 코드만 읽고 실행 동작까지 완료로 과장하지 않는다. 반대로 핵심 경로가 명백히 없는 경우 단순 미검증으로 흐리지 않는다.
- 기존 검증 기록은 실행 대상·코드 버전·입력·범위가 현재 요구에 유효할 때만 사용한다. 현재성이나 범위가 불명확하면 설명에 표시한다.
- 검증 근거에 검사 당시의 커밋과 관련 미커밋 변경 상태, 또는 관련 파일 해시를 연결한다. 기존 기록을 재사용하고 같은 코드 상태를 항목마다 중복 기록하지 않는다.
- 항목별로 원문 위치, 구현 파일·함수 또는 경로, 테스트·실행 기록을 연결한다. 확인되지 않은 수치·파일·행 번호를 만들지 않는다.

## 4. 검증 실행 범위

- 기존 코드·기록을 먼저 확인하고 핵심 불확실성을 해소할 최소 검사를 선택한다. 모든 테스트를 무조건 반복하지 않는다.
- 실행이 필요하면 기존 테스트·빌드·조회 등을 사용할 수 있다. 계정·DB 변경이 필요한 검사는 임시 환경에서 수행하고 기존 데이터나 프로세스를 훼손하지 않는다.
- 단위·모의·로컬 통합·실제 외부 연동·수동 검사를 구분한다. 모의 검사만 했다면 실제 외부 연동까지 완료로 보고하지 않는다.
- 점검을 통과시키려고 앱 코드·설정·원본 데이터·테스트 기대값을 수정하지 않는다. 실패는 근거와 함께 보고한다.
- 환경이 막히면 이유와 재현 명령을 남긴다. 도구·데몬이 없다는 이유를 구현 실패와 혼동하지 않는다.
- 일반적인 외부 배포·메시지 전송·운영 데이터 변경은 이 점검의 범위가 아니다.

## 5. 결과 제시

먼저 중요한 누락·차이를 짧게 말하고 다음 표로 정리한다. 전체 파일이나 로그를 붙이지 않는다.

| 요구사항 | 상태 | 구현·검증 근거 | 남은 작업 |
|---|---|---|---|

- 복잡한 과제는 요구 분류별로 묶되 원문의 필수 항목을 누락하지 않는다.
- 남은 작업을 ‘필수 누락·명확한 위반 → 핵심 검증 공백 → 제출 문서·설명 불일치’ 중심으로 정렬한다. 선행 작업과 영향도에 따라 조정한다.
- 구현이 필요한 작업과 검증만 필요한 작업을 구분한다. 추가 권장사항은 원문 필수 요구와 분리하고 필요한 것만 제시한다.
- 중요한 검증 결과에는 입력·기대 동작·관찰 동작·재실행 명령 또는 수동 절차를 남긴다. 기존 실행 기록이 있으면 위치를 연결하고 실행하지 않은 결과나 종료 코드를 만들지 않는다.
- 필요하면 원문 기준과 사용자 변경 기준의 차이를 한 줄로 적는다.
- 파일 보고서는 사용자가 요청하거나 과제에서 필요할 때 작성한다. 그렇지 않으면 대화로 결과를 제공한다.

## 6. 후속 작업

- 점검 완료 후 자동으로 구현·수정·커밋하지 않는다. 사용자가 선택한 작업만 이어간다.
- ‘다음’만으로 새로운 코드 수정 권한을 추정하지 않는다. 현재 점검의 다음 항목은 이어서 확인하되 수정 범위가 불명확하면 필요한 선택을 묻는다.
- 수정 후 재점검을 요청하면 변경 영향과 이전 미완료 항목을 중심으로 갱신한다. 근거 없이 전체 완료로 바꾸지 않는다.
- 사용자가 결함 수정을 요청한 경우에만 재현 검사를 남기고 승인된 범위를 수정한 뒤 동일 검사를 실행한다. 기대값·fixture·검사 자체를 변경했다면 변경 이유와 새 기준을 명시하고 이전 통과 이력을 그대로 재사용하지 않는다.
