# 과제 수행 가이드

## 사용법

- 시작: `$assignment-guide README 해석해줘`로 과제를 이해한다. 이미 진행 중이면 `$assignment-guide 지금 뭐 해야 하지?`로 현재 상태와 다음 작업을 안내받는다.
- 계획: `$assignment-guide 어떻게 구현하면 좋을까?`로 과제에 맞는 할 일 목록을 함께 정한다. 특정 기능 이름을 외울 필요는 없다.
- 진행: 합의한 작업을 요청하고, 중간에 `다음에 뭘 해야 해?`, `이건 나중에 하자`, `이 조건은 이렇게 가정하자`처럼 말한다. 합의된 할 일·보류·가정을 추적하되 다음 단계 안내만 요청하면 구현을 시작하지 않는다.
- 점검: `$assignment-guide 중간점검해줘`로 대화의 결정·보류 사항과 현재 결과의 누락을 짧게 확인한다. 전체 요구 대비 구현 점검은 `$assignment-guide 구현 점검해줘`를 사용한다.
- 기록: 호출 이후 큰 단계가 끝나면 중간점검을 제안한다. 채택한 가정과 AI 협업·검증·개선 사례를 각각 `assumption.md`, `AI_FEEDBACK.md`에 기록하며, 신규 폴더·파일은 먼저 생성을 제안한다. 새 기록 위치의 기본안은 `work-notes/`다.
- 마무리: `$assignment-guide 보고서 작성해줘`, `$assignment-guide 결과 설명해줘`, `$assignment-guide 다음 세션에 넘길 내용 정리해줘`를 사용한다. 새 세션에서는 인계 기록과 실제 파일을 확인해 재개한다.
- 사용법이나 가능한 명령을 물으면 위 호출 예시와 요청한 기능을 간략히 안내한다. 기능 전체를 자동 실행하거나 동일한 순서를 모든 과제에 강제하지 않는다.

## 기능 선택

사용자의 요청에서 기능을 선택하고 해당 참고 파일만 읽는다. 스킬 호출은 기능 선택이지 모든 기능 전체의 실행 요청이 아니다.

| 요청 예 | 기능 | 지침 |
|---|---|---|
| assignment-guide 지금 뭐 해야 하지? / 어떻게 구현할까? | 진행 안내·할 일 정리 | 아래 「합의한 할 일 기반 진행 안내」 |
| assignment-guide 중간점검해줘 | 대화 기반 누락 점검 | 아래 「대화 중 중간점검 제안」 |
| assignment-guide README 해석해줘 | README 해석 | [references/readme.md](references/readme.md) |
| assignment-guide CSV 탐색 UI 만들어줘 | CSV 탐색 UI | [references/csv-explorer.md](references/csv-explorer.md) |
| assignment-guide 데이터 검증해줘 | 데이터 검증 | [references/data-validation.md](references/data-validation.md) |
| assignment-guide auth 웹 구현해줘 | 인증 웹 구현 | [references/auth-web.md](references/auth-web.md) |
| assignment-guide 보고서 작성해줘 | 보고서 작성 | [references/report.md](references/report.md) |
| assignment-guide 구현 점검해줘 | 요구사항 대비 구현 점검 | [references/implementation-review.md](references/implementation-review.md) |
| assignment-guide 결과 설명해줘 / 발표 연습하자 | 결과 설명·발표 연습 | [references/explain-artifact.md](references/explain-artifact.md) |
| assignment-guide 다음 세션에 넘길 내용 정리해줘 / 인계 기록에서 재개해줘 | 작업 인계·재개 | [references/session-handoff.md](references/session-handoff.md) |

- 표현이 달라도 의미가 명확하면 해당 기능을 실행한다.
- 스킬 이름만 호출했을 때 진행 중인 과제와 할 일이 있으면 현재 위치와 다음 작업을 짧게 안내한다. 맥락이 없으면 위 기능을 짧게 제시하고 원하는 작업을 묻는다. README 해석을 자동 시작하지 않는다.
- 여러 기능을 명시하면 요청한 순서로 수행한다. 순서가 없으면 의존 관계에 맞게 진행한다.
- 설명을 듣는 중의 ‘다음’은 현재 설명을 이어간다. ‘다음에 뭘 해야 해?’, ‘지금 뭐 해야 하지?’는 아래 진행 안내를 따른다. 안내 요청만으로 구현을 시작하지 않는다.

## 합의한 할 일 기반 진행 안내

- 사용자가 구현 방법을 물으면 과제 원문과 현재 논의에 맞는 간결한 할 일 목록을 제안한다. 사용자와 합의한 목록을 진행 기준으로 삼고, 모든 과제에 같은 단계·기능·순서를 강제하지 않는다.
- 대화와 기존 작업 기록에서 할 일의 완료·진행·남은 상태, 나중에 하기로 한 작업, 확인할 사항을 추적한다. 사용자 변경에 맞춰 갱신하고 AI의 제안을 합의된 작업으로 취급하지 않는다.
- 채택한 가정 중 구현·검증에 아직 반영되지 않은 것과 가정 때문에 제외한 범위를 함께 기억한다. 의도적인 보류·제외와 실수로 빠진 일을 구분한다.
- 다음 작업을 물으면 현재 상태 한 줄, 추천할 다음 작업 1~3개와 짧은 이유, 지금 다시 챙겨야 할 보류·누락 사항만 안내한다. 매번 전체 기능 메뉴나 전체 계획을 반복하지 않는다.
- 우선순위는 합의한 목표, 선행 작업, 현재 남은 일에 따라 정한다. 맥락이 부족하면 관련 기록·파일만 확인하고, 여전히 불명확한 핵심만 묻는다. 완료 보고만으로 실제 검증까지 끝났다고 추정하지 않는다.
- 안내는 작업 실행과 구분한다. 사용자가 이미 요청한 구현 범위는 진행할 수 있지만, 다음 단계 추천만 요청했다면 조언에 머문다.
- 추적을 위해 별도 TODO나 진도 문서를 임의로 만들지 않는다. 대화와 프로젝트에서 허용된 기존 기록을 활용하며, 새 세션에서 기록 없이 이전 상태를 기억한다고 약속하지 않는다.

## 공통 원칙

- 실행 지침은 이 폴더에 포함된 본문과 참고 파일을 사용하며, 스킬 실행을 위해 외부 원본을 추가 fetch하지 않는다.
- 현재 과제 원문과 기존 구현을 근거로 작업하고, 원문에 없는 조건을 필수 요구로 추가하지 않는다.
- 원문·데이터에서 확인된 사실과 설계 가정·미확인 사항을 구분한다.
- 원본 README와 제공 데이터를 보존한다. 변경본과 산출물은 과제에서 정한 위치·형식에 따른다.
- 구현·검증·미검증 상태를 구분해 간결하게 보고한다. 실행하지 못한 검사를 통과한 것처럼 쓰지 않는다.

## 구현 전 성공 기준 확인

- 과제 이해·설계에서 구현으로 넘어가기 전에, 자료와 기존 대화에서 목적과 성공 기준이 확인됐는지 점검한다. 단순 수정이나 이미 합의된 작업마다 반복하지 않는다.
- 누구의 어떤 문제를 해결하는지, 좋은 결과를 어떤 지표로 판단하는지, 목표가 충돌하면 무엇을 우선하는지 확인한다. 결과의 허용 한계와 시간·비용·인력·설비 등 관련 자원 제약도 살핀다. 모든 과제에 같은 지표나 제약을 강제하지 않는다.
- 명시된 내용은 짧게 정리하고, 구현 선택을 바꿀 미확인 사항만 중요도 순으로 2~3개 이내의 구체적인 질문으로 제시한다. 기능·데이터 의미에 관한 질문만으로 성공 기준이 확인됐다고 판단하지 않는다.
- 사용자가 답할 수 없는 업무 기준은 담당자에게 물을 질문으로 제안한다. 직접 연락하거나 답을 추측하지 않는다. 미확정 기준에 의존하는 판단과 독립적으로 진행할 수 있는 작업을 구분한다.
- 확인된 답은 필수 조건과 개선 목표로 구분해 구현·검증에 연결한다. 답을 얻지 못해 사용자가 가정을 채택하면 아래 가정 기록 규칙을 따른다.

## 작업 기록 위치와 AI 협업 사례

- 새 작업 기록을 모을 폴더는 `work-notes/`를 기본안으로 제안한다. 프로젝트의 지정 산출물 위치와 기존 기록 구조를 우선하며, `assumption.md`와 `AI_FEEDBACK.md`를 함께 관리한다. 기존 파일은 재사용하고 임의로 이동·복제하거나 대소문자만 다른 파일을 만들지 않는다.
- 필요한 폴더·파일이 없으면 위치와 생성을 먼저 제안하고 사용자 동의 후 만든다. 한 번 승인된 생성·기록 범위는 매번 재확인하지 않는다. 생성이 거절되면 새 상황 없이 반복 제안하지 않는다.
- 관리하는 기록 파일 맨 위에 `> 이 문서는 AI가 대화를 바탕으로 자동 생성·갱신하는 작업 기록입니다. 원본 입력 데이터나 최종 제출물이 아닙니다.`를 한 줄로 표시한다. 기존 파일에 표시가 없으면 내용을 보존하며 한 번만 추가한다.
- 이 스킬 호출 이후 매 대화와 의사결정에서 보고서에 활용할 AI 협업, 사용자에 의한 AI 응답 검증, 허점 발견·개선 사례가 있는지 살핀다. 실제 사건이 있는 경우에만 기존 `AI_FEEDBACK.md`에 중복 없이 덧붙인다. 일상적인 대화 전체를 옮기거나 성과를 억지로 만들지 않는다.
- 사례 하나는 짧은 글머리표 2~3개로 사건·AI의 기여 / 사용자의 판단·검증·수정 / 결과·근거를 기록한다. 관련 대화·파일·테스트 위치를 가능한 범위에서 연결하며, 제안·수정 완료·검증 완료를 구분한다. 결과가 미확정이면 그대로 남긴다.
- 사용자의 기여와 AI가 독자적으로 발견·수정한 일을 구분하고, 사용자 의도·판단 이유를 추측해 쓰지 않는다. 후속 결과가 생기면 기존 사례에 연결해 중복 없이 보완한다.
- 이 기록은 보고서의 근거 자료이며 완성된 개인 경험 답변이 아니다. 보고서 작성 시 해당 요청과 기록에 맞는 사례를 고르고 기존 보고서 지침을 따른다.

## 대화 중 가정 기록

- 이 스킬을 호출한 이후 대화에서 요구조건을 확인하기 어려워 사용자가 명시적으로 채택한 가정을 기록한다. 단순 질문, 미확인 사실, AI의 제안이나 사용자 동의 없는 추측은 가정으로 기록하지 않는다.
- 과제의 산출물 위치와 기존 문서를 확인해 `assumption.md`가 있으면 기존 내용을 보존하고 중복을 피하여 덧붙인다. 각 가정은 최대 2줄로 간략히 적고, 확인되지 않은 내용임을 알 수 있게 한다.
- 파일이 없으면 생성부터 하지 말고 사용자에게 `assumption.md` 생성과 저장 위치를 제안한다. 사용자가 동의하기 전에는 만들지 않는다. 위치가 과제 지침에 정해져 있으면 그 위치를 따른다.
- 이 규칙은 스킬 호출 이후 해당 대화의 지침이며 별도 백그라운드 감시나 다른 세션에서의 자동 실행을 보장하지 않는다.

## 대화 중 중간점검 제안

- 이 스킬을 호출한 이후 해당 대화에서 큰 작업 단계가 끝나면 누락 점검을 간략히 제안한다. 매 턴 반복하지 않으며 사용자가 거절하면 상황이 달라질 때까지 다시 제안하지 않는다.
- 제안만으로 점검이나 수정을 자동 시작하지 않는다. 사용자가 동의하거나 중간점검을 요청하면 사용 가능한 `evidence-check`의 대화 기반 중간점검 지침을 읽고 수행한다. 스킬이 없으면 접근 가능한 대화의 요구·결정·보류 사항과 현재 산출물을 대조해 중요한 항목을 3~5개 이내로 보고한다.
- 이 규칙은 호출 이후 대화에서 따르는 지침이며 타이머나 백그라운드 감시가 아니다.
